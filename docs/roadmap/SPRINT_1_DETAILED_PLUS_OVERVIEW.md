## القرار المعماري المطلوب منكم — 3 خيارات حقيقية، لا رابع

### الخيار أ: Hard Block (حجب صارم)
المحرك يرفض الكتابة تمامًا لو الموافقة غير ممنوحة — يرجّع خطأ واضح (403) للجهاز.
- ✅ الأكثر أمانًا قانونيًا (COPPA/GDPR-K صريحان في هذا)
- ❌ **خطر تكسير حقيقي:** أي عائلة مسجَّلة حاليًا **بدون** موافقات مُسجَّلة صراحة (كل العائلات التجريبية اللي أنشأناها في الاختبارات، وربما عائلات حقيقية مستقبلية لم تمر بشاشة موافقة بعد) ستتوقف ميزاتها فجأة

### الخيار ب: Soft Warn (تنبيه فقط)
الكتابة تستمر، لكن تنبيه واضح يظهر للأب في الـ Dashboard: "بيانات [الميزة] تُجمَع بدون موافقة صريحة مُسجَّلة".
- ✅ صفر خطر تكسير فوري
- ❌ لا قيمة قانونية حقيقية — مجرد واجهة، لا حماية فعلية

### الخيار ج: Default-Implicit + Opt-Out صريح (المُوصى به هندسيًا)
عند التسجيل الأول للعائلة، تُمنح كل أنواع الموافقة الأساسية تلقائيًا (شاشة تسجيل واضحة تقول "بالمتابعة، أنت توافق على...")، مع زر صريح "إدارة الموافقات" في Settings للسحب الفردي لأي نوع وقتها.
- ✅ يوازن بين الاستمرارية والحماية القانونية الحقيقية
- ✅ **يحتاج شاشة تسجيل جديدة تُوثِّق الموافقة الصريحة وقت الإنشاء** (سبرنت UI حقيقي، لا مجرد Backend)
- ⚠️ لا يزال يحتاج تأكيدًا قانونيًا: هل "الموافقة الضمنية عند التسجيل" مقبولة في نطاقكم القضائي (Saudi PDPL تحديدًا)؟

**توصيتي الهندسية: الخيار ج** — لكن هذا قراركم، ليس قراري.

# الجزء الثاني: نظرة تنفيذية على السبرنتات 2-10

| Sprint | أول 3 مهام تنفيذية فعلية | نقطة الحسم الرئيسية |
|---|---|---|
| **2. الفوترة** | شاشة خطط الاشتراك → شاشة دفع (بوابة واحدة أولًا، مثلًا Stripe) → شاشة الفاتورة/التاريخ | أي مزوّد دفع نبدأ به من الـ 7 الموجودين؟ (يعتمد على السوق المستهدَف فعليًا) |
| **3. تكافؤ التطبيقين** | جرد مقارن شاشة-بشاشة → تصنيف كل فجوة (مقصودة/حقيقية) → تنفيذ الفجوات الحقيقية بس | لا تنفيذ قبل الجرد — قد لا توجد فجوة حقيقية أصلًا |
| **4. الموثوقية** | اختيار أداة (Sentry مجاني كافٍ للبداية) → دمج SDK بالتطبيقين → Dashboard تنبيهات | قرار أداة واحدة بس، لا تعقيد |
| **5. Push** | مشروع Firebase جديد → دمج FCM Android → ربط الأحداث الخمسة الحرجة | Backend محتاج تخزين FCM Token لكل جهاز (حقل جديد بسيط) |
| **6. الدعم الفني** | صفحة أسئلة شائعة ثابتة → نموذج تواصل بريدي → ربط بريد دعم حقيقي | لا نظام Ticketing معقَّد — MVP بسيط يكفي الإطلاق |
| **7. Onboarding** | **يحتاج جهاز Android حقيقي** — تسجيل الفيديو الكامل للتدفّق، تحديد نقاط الاحتكاك الفعلية | أول سبرنت غير قابل للتنفيذ الكامل هنا |
| **8. iOS** | **يحتاج macOS/Xcode** — غير قابل للتنفيذ هنا إطلاقًا | Parent App (Flutter) أولًا، أسهل نسبيًا من Child App |
| **9. QA حقيقي** | **يحتاج أجهزة حقيقية متعددة** | نقطة التحويل من "كود" لـ"منتج" |
| **10. الإطلاق** | سياسة خصوصية معتمدة قانونيًا → حسابات مطوّرين → لقطات شاشة حقيقية | قرار قانوني نهائي، ليس هندسيًا |
